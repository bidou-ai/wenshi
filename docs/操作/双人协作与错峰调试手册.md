# 双人协作与错峰调试手册

更新时间：2026-09-08

## 1. 目的

本手册用于两个人在不同时间、不同地点或不同终端与 Codex 对话时，保持项目上下文一致，避免重复修改、误删数据、错误启动硬件、把未验证内容写成已完成。

项目目录：

```bash
/home/ubuntu/jaka/wenshi
```

两个人可以分别称为：

- **操作者 A**：负责现场设备、相机、AGV、JAKA 和现场日志。
- **操作者 B**：负责代码、数据集、标注、训练、文档和离线验证。

角色可以轮换，但每次会话必须明确当前是谁、正在做什么、是否接触硬件。

## 2. 每次对话第一句话

每次新开 Codex 对话，必须先发送以下信息：

```text
我是操作者 A/B。
当前日期和时间：
当前地点：现场 / 办公室 / 仅离线
本次目标：
是否允许连接或启动硬件：是 / 否
我提供的最新证据：日志路径、命令输出或文件路径
本次不允许做的事：
```

示例：

```text
我是操作者 A。
当前日期和时间：2026-09-08 14:30
当前地点：现场
本次目标：只检查 D435 图像，不运动 AGV/JAKA
是否允许连接或启动硬件：允许相机，不允许运动
最新证据：刚刚的 camera.log
本次不允许做的事：不要修改配置，不要启动正式表型
```

## 3. 开始工作前的固定规则

Codex 每次开始工作必须：

1. 读取 `AGENTS.md` 和[思考与协作规范](../思考与协作规范.md)。
2. 检查 `git status`，识别已有改动。
3. 读取与当前目标相关的代码、配置、日志和现行文档。
4. 判断任务是离线任务、相机任务、现场测试还是正式表型任务。
5. 说明将修改哪些文件、是否会连接硬件、如何验证。

两个人都必须遵守：用户已经提供的日志和命令，Codex 应直接检查仓库，不要让用户重复执行本机可以完成的分析。

## 4. 任务分工

### 4.1 操作者 A：现场任务

允许负责：

- 相机健康、有效帧和图像质量检查。
- 按现场安全清单执行人工移动、示教和硬件测试。
- 提供现场日志、照片、屏幕现象和准确时间。
- 记录急停、报警、超时、阻挡、姿态异常和恢复过程。

不得自行改变：

- 正式 Tag 映射。
- 正式路线参数。
- `phenotyping.enabled`。
- 模型发布文件。
- 未经过交接的代码。

### 4.2 操作者 B：代码与数据任务

允许负责：

- 离线检查、代码修改、单元测试和集成测试。
- 数据审计、标注规则、训练副本、模型训练和错误分析。
- 文档更新和 Git 提交。
- 根据现场证据提出下一步测试命令。

不得在未明确授权下：

- 启动 AGV、JAKA 或现场表型任务。
- 修改现场安全限制。
- 把模拟、教学或路线测试写成正式验收。
- 用新数据覆盖原始数据。

## 5. 任务锁和交接

### 5.1 开始前登记

同一时间只允许一个人修改同一个文件。开始前在对话中登记：

```text
[任务锁]
操作者：
开始时间：
任务：
将修改的文件：
预计结束：
禁止另一位操作者修改：
```

文件级锁示例：

```text
操作者 B 锁定：
README.md
docs/技术/项目状态.md
yubei/train_yolo.py
```

### 5.2 结束时交接

```text
[交接完成]
操作者：
结束时间：
已完成：
未完成：
修改文件：
测试命令及结果：
现场动作及结果：
生成的日志/数据路径：
当前风险：
下一步：
是否已提交 Git：
提交号：
```

没有交接记录时，下一位操作者只能做只读检查，不能继续修改同一批文件。

### 5.3 交接状态词

只使用以下状态：

- `进行中`：有人持有任务锁。
- `待验证`：代码或数据已经改变，但验证尚未完成。
- `现场待确认`：需要现场人员操作或测量。
- `已验证`：有明确命令、日志或数据证据。
- `已放行`：经过项目约定的发布或现场验收。
- `已归档`：不再作为当前入口，但保留追溯。

“完成”“没问题”“应该可以”不能代替证据。

## 6. 对话和修改纪律

### 6.1 一次对话只处理一个主目标

推荐把任务拆成以下类型之一：

```text
离线审查
代码修复
数据采集
数据标注
模型训练
现场相机检查
现场示教/机械臂测试
路线测试
正式表型验收
文档整理
```

发现新问题时先记录，不要在同一轮顺手改变无关模块。

### 6.2 修改代码时

必须按以下顺序：

1. 说明问题、影响范围和风险。
2. 先写或定位回归测试。
3. 修改最小必要范围。
4. 运行针对性测试。
5. 再运行完整测试或说明无法运行的原因。
6. 更新受影响的唯一现行文档。
7. 写交接记录。

原始数据、现场日志和已存在的用户改动不能重置或覆盖。

### 6.3 修改文档时

先找现有权威文档，再决定是更新它还是新增入口。不要同一事实在多个文档中写出互相独立的版本。新文档放在 `docs/`，文件名使用中文；根目录只保留 GitHub 必需的 `README.md`。

## 7. 现场调试流程

### 7.1 现场前

操作者 A 先确认：

- 工作空间无人进入，急停位置明确。
- AGV、JAKA、D435、电源、网线和 Wi-Fi 状态明确。
- 当前是否允许相机、底盘、机械臂或正式表型动作。
- 当前测试对应哪份清单和哪一个日志目录。

操作者 B 先确认：

- 没有未交接的代码改动。
- 本次要运行的入口和参数。
- 现场测试不会覆盖正式配置和正式运行目录。
- 已准备好记录时间、命令、日志和异常。

### 7.2 现场中

任何人员进入工作区、急停、报警、通信中断、定位过期、相机断流或姿态异常时：

1. 现场人员先执行实体急停并确认 AGV/JAKA 停止。
2. 再输入软件 `stop`。
3. 记录发生时间、当前位置、命令、日志和恢复动作。
4. 未确认原因前不重复运动。

现场测试入口：

```bash
cd /home/ubuntu/jaka/wenshi
./scripts/start_field_test.sh
```

该入口用于现场测试，不等于正式表型任务。示教只保存点位，不能据此证明三视角表型姿态已经验收。

### 7.3 现场后

现场人员把完整日志目录、现象、实际动作和结果交给代码人员。代码人员只在离线状态下分析并修改代码；需要再次现场确认的内容标成 `现场待确认`。

## 8. 数据和模型协作流程

两套模型必须分开：

```text
rice_plant：整株水稻
panicle：单个稻穗
```

标准顺序：

```text
采集
-> capture audit
-> 标注
-> 质量复核
-> 按 plant_id/capture_batch 分组
-> prepare
-> train
-> 独立测试
-> 错误分析
-> 第二轮训练
-> 人工复核
```

规则：

- 训练采集当前不需要 Tag。
- 原始图片不覆盖，规范化图片写入新目录。
- 同一株不能拆到 train 和 val。
- 连拍只有在清晰度、姿态或遮挡信息不同的时候才全部保留。
- 稻穗必须一穗一框，边界无法判断时标记歧义。
- 检测框数量不能直接当最终有效穗数。
- 模型没有通过独立测试和人工复核前，不得发布或开启正式表型。

日常离线入口：

```bash
cd /home/ubuntu/jaka/wenshi
./yubei/start_yubei.sh daily-check
```

## 9. Git 协作流程

开始前：

```bash
cd /home/ubuntu/jaka/wenshi
git status --short
git branch --show-current
```

提交前：

```bash
git diff --check
PYTHONPATH=app:. python3 -m pytest -q
```

提交信息要说明事实，例如：

```text
docs: add project audit and two-person workflow
fix: handle field test teaching timeout
data: add independent panicle validation set
```

提交后交接：

```text
分支：
提交号：
提交内容：
测试结果：
未提交文件：
是否允许下一位继续：
```

推送 GitHub 前必须确认：

- 当前分支和远程仓库正确。
- 没有把运行日志、缓存、私密配置或未确认模型推送进去。
- 两位操作者都知道将要推送的提交。
- 推送后记录远程分支和提交号。

## 10. 常见冲突处理

### 发现另一人正在修改同一文件

停止编辑，先 `git status` 和 `git diff`，把冲突文件登记为锁定文件。不能用 `reset --hard`、`checkout --` 或覆盖式复制解决。

### 发现代码已经改了但没有交接

只读检查现状，记录修改文件和测试状态，询问原操作者意图；不要假设这些改动可以删除。

### 现场现象和代码日志矛盾

以原始现场时间、完整日志和实际视频/照片为优先证据，保留矛盾，先标记 `待验证`，不要直接改代码迎合单次现象。

### 用户说“模型 OK”

先区分：

- 训练是否结束。
- 验证集指标是否存在。
- 是否有独立测试集。
- 是否做过人工错误分析。
- 是否达到项目放行标准。

只有这些条件明确后，才能使用“已放行”。

## 11. 每日最小流程

### 离线日

```bash
cd /home/ubuntu/jaka/wenshi
./yubei/start_yubei.sh daily-check
git status --short
```

然后只处理一个数据、模型、代码或文档任务，并写交接记录。

### 现场日

1. 先读[安全约束](安全约束.md)和[现场验收清单](现场验收清单.md)。
2. 明确只允许相机、示教、机械臂、路线中的哪一类动作。
3. 启动现场入口并记录日志目录。
4. 一项测试完成后再进入下一项。
5. 任何异常先停机，再记录，再分析。
6. 结束时交接，不把口头结论留在聊天里。

## 12. 双人交接的最终原则

项目共享的不是“某个人记得什么”，而是仓库中的证据：

- 当前状态写进 `docs/技术/项目状态.md`。
- 详细流程写进对应操作手册。
- 现场事实保留日志和现场测试记录。
- 代码行为由测试证明。
- 数据处理由 manifest、标签和训练报告证明。
- 未完成事项明确写成阻塞项。

这样两个人即使错峰工作，下一次对话也能从同一个事实起点继续。
