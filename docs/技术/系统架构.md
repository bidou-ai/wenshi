# 系统架构

## 当前范围

系统的现行目标是 32 株水稻的株高和有效穗数。布局为 `A`、`B-L`、`B-R`、`C` 四排各八株；自动株高测试只检测 A、B-L、B-R 共 24 株，C 排保留登记但排除检测。16 个观测组按 `left-01..08`、`right-01..08` 排列，每组覆盖配置中的主动株、每株三视角。

```text
配置与预检 -> 16 组调度 -> Tag 身份/局部触发 -> 底盘停稳
-> 两株各三视角 RGB-D -> 单株证据存储 -> 候选计算 -> 人工复核与导出
```

该图描述目标流程，不表示正式表型运动编排已经完成或现场验收。

## 职责边界

| 层 | 代码或组件 | 责任 |
| --- | --- | --- |
| 硬件 | AGV、JAKA、Windows D435 服务、`camera_bridge.py` | 状态、运动和 RGB-D 数据边界 |
| 路线与安全 | `route_controller.py`、`control/`、`hardware_check.py` | 地图、限速、状态新鲜度和互锁 |
| 表型配置与调度 | `phenotyping/config.py`、`schedule.py` | 32/16 验证与逻辑观测顺序 |
| 表型数据与算法 | `capture_schema.py`、`plant_store.py`、`tag_adapter.py`、`plant_height.py`、`effective_panicles.py` | 证据、候选和复核；没有运动权限 |
| 后台 | `dashboard/` | 只读查看和 CSV 导出；没有运动接口 |

一键现场通道位于 `app/wenshi_patrol/height_test/`：`models.py` 是无硬件领域类型，`algorithms.py` 只消费 RGB-D/检测结果，`capture.py` 负责 D435 和双 YOLO，`storage.py`/`report.py` 保留证据，`setup.py` 发布现场映射，`runner.py` 才通过窄适配器编排 AGV/JAKA，`cli.py` 提供 setup、arm-only、full-route、replay、report。replay 不导入或连接运动客户端。

只有高层控制器可以同时持有 AGV 与 JAKA 运动客户端。表型算法、存储和后台只能返回数据状态，不能决定或发起机器人运动。旧 `rice` 抵近、倒车、J5 跟随和固定抵近是历史原型，不属于本架构的表型执行路径。
