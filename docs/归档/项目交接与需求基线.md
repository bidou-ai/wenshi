# Wenshi 项目交接说明：株高与有效穗观测

> 本文件用于另一台电脑上的 Codex 接手项目。开始修改代码前必须完整阅读本文件，以及“必须先阅读的现有文件”一节列出的内容。
>
> 本文件记录的是 2026-08-27 前已经确认的需求、现有代码事实、建议的改造方向和仍待现场确认的事项。不要把“待确认”内容当作已确定参数直接写入正式配置。

## 1. 先理解我们现在要做什么

项目早期围绕“花时检测”进行了代码准备，但和水稻杂交中心进一步沟通后，短期范围已经调整。

### 1.1 初期最终确定的两个表型

初期只做：

1. **株高**
2. **有效穗数**

本期暂不做：

- 花时自动识别；
- 颖壳张角；
- 柱头外露率与柱头颜色；
- 4D Gaussian Splatting 或其他 3D/4D 展示；
- 短信、微信提醒；
- 穗粒数、粒型、结实率；
- 叶片取样、茎秆切断或其他破坏性测量；
- 其他尚未明确进入短期验收范围的表型。

不要因为仓库里已有 `flower` 类别、目标抵近状态机或花时讨论文档，就把短期任务重新扩展为花时项目。

### 1.2 株高的已确定口径

株高不是图像中的垂直高度，也不是“水面到画面最高点”的直线距离。

人工测量口径为：

> 从水面开始，沿同一根茎秆和穗轴量到最高穗顶；如果穗或茎秆下垂，按人工拉直后的路径长度计算。

因此软件需要表达和计算的是一条三维曲线的弧长：

```text
水面基准
  -> 同一根茎秆中心线
  -> 同一穗轴
  -> 最高穗顶
  -> 沿路径累加长度
```

现场允许使用卡槽顶部作为稳定视觉基准。卡槽顶部与水面之间的高度差由现场人工测量，再作为补偿值加入结果。这个补偿值尚未标定，不能写死。

第一阶段接受半自动结果：

- 系统生成候选起点、最高穗顶和中心线路径；
- 后台把候选路径叠加在图片上；
- 人工确认或修改路径；
- 人工确认后的值作为正式株高；
- 自动值、人工值和差值都要保留。

### 1.3 有效穗数的已确定口径

有效穗采用当前项目组与老师确认的操作口径：

> 统计一株中能够看清楚并确认已经长出来的穗子。

第一阶段允许输出：

- 确认有效穗；
- 疑似穗；
- 被遮挡或无法判断的穗；
- 跨视角可能重复的穗；
- 人工最终有效穗数。

不能把三个视角中检测到的穗子数量直接相加。同一穗可能出现在多个视角中，必须进行跨视角合并和去重，并允许人工合并、拆分、新增或删除标记。

### 1.4 机器人在本项目中具体做什么

机器人短期任务是：

> 按固定环路依次到达 24 株水稻附近，确认植株身份，停车后用机械臂带动 D435 从少量固定角度拍清整株、茎秆和穗子，保存可追溯的 RGB-D 数据；随后分别计算株高和有效穗数，并由人工复核。

机器人主要减少：

- 人工反复在温室内走动；
- 人工逐株寻找和确认位置；
- 人工重复调整拍摄角度；
- 图片、株号、测量值和批次记录之间的人工整理工作。

第一阶段不是“完全无人测量”。第一阶段目标是完成稳定采集、自动候选结果、人工确认和误差记录，证明系统可以可靠地覆盖 24 株。

## 2. 已确认的温室布局和运行边界

### 2.1 植株布局

总计 24 株：

```text
左区          中间区          右区
1 行 x 6 株   2 行 x 6 株     1 行 x 6 株
```

可以理解为：

```text
左区      中间左排  中间右排      右区
6 株        6 株      6 株         6 株
```

### 2.2 机器人路线

机器人仍然只围绕中间区域运行：

- 最左、最右外侧通道狭窄，机器人不能进入；
- 机器人从中间区左侧通道观察左区和中间左排；
- 机器人从中间区右侧通道观察中间右排和右区；
- 普通环路保持正向运动，不因表型算法任意倒车；
- 现有地图路线和现场安全约束必须保留。

### 2.3 当前建议的停车组织方式

不要为 24 株建立 24 个 AGV 地图站点。

当前建议为 12 个逻辑停车位置：

- 左侧通道 6 个位置：每个位置处理左区 1 株和中间左排对应 1 株；
- 右侧通道 6 个位置：每个位置处理中间右排 1 株和右区对应 1 株；
- 一次停车处理通道两侧相对的两株；
- 12 次停车覆盖 24 株。

这里的“12 个位置”是当前控制方案，不是已经现场测量完成的地图坐标。现场仍需标定每个位置的大致沿线范围、减速区间和拍摄触发条件。

### 2.4 AprilTag 已确定

项目采用 AprilTag 作为单株身份标识。

当前已有 Tag 图片，原始路径为：

```text
D:\my gz\tag\tag
```

Tag family 为 `tag25h7`，现有文件包含 `tag25h7_0.png` 到 `tag25h7_100.png`，数量足够。

注意：这个路径在另一台电脑上可能不存在。不要在正式代码中写死该绝对路径。需要把实际采用的 Tag ID 与植株信息写入项目配置，并提供导入/校验方式。

Tag 的职责：

- 确认当前植株或当前相对植株对的身份；
- 检查巡检顺序是否正确；
- 提供局部相对位置和尺度参考；
- 将图片和测量结果绑定到唯一株号。

Tag 不应单独承担整条路线导航。建议采用：

```text
AGV 地图位置和沿线进度 -> 粗定位和提前减速
AprilTag                  -> 身份确认和局部触发
```

必须先做 Tag 解码兼容性验证。已发现当前一台 Windows Python 环境中的 OpenCV `aruco` 模块没有内置 `DICT_APRILTAG_25h7`。不要假设任意 OpenCV 版本都能直接识别 `tag25h7`。Tag 检测必须封装成独立适配器，并选择经过测试的检测库或实现。

Tag ID 到植株的映射尚未最终确认。可以提出如下候选映射，但在用户批准前不要写入正式配置：

```text
0-5    -> 左区 6 株
6-11   -> 中间左排 6 株
12-17  -> 中间右排 6 株
18-23  -> 右区 6 株
```

## 3. 当前项目代码事实

项目根目录是本文件所在目录。当前下载内容可能来自 GitHub ZIP，未必包含 `.git` 历史；先检查实际环境，不要假设有 Git 提交记录。

### 3.1 已有正式入口

- `scripts/start_wenshi.sh`：正式巡检入口；
- `scripts/start_field_test.sh`：现场相机、示教、路线和机械臂测试入口；
- `scripts/start_dashboard.sh`：后台入口；
- `yubei/start_yubei.sh`：准备、采集、标注、训练和示教工具入口；
- `windows/windows_realsense_server.py`：D435 所在 Windows 电脑的 HTTP RGB-D 服务。

不要无理由增加多个日常启动脚本。最终日常运行仍应保持一个正式入口；现场标定和测试可以保留独立入口。

### 3.2 已有硬件和安全层

`app/wenshi_patrol/` 中已有：

- `agv.py`：AGV 状态与连续运动；
- `jaka.py`：JAKA TCP 客户端；
- `arm_controller.py`：机械臂巡视、固定路径、回撤和目标跟随；
- `camera_bridge.py`：Windows D435 HTTP 服务到 ROS2 的桥；
- `hardware_check.py`：AGV/JAKA/D435 连通检查；
- `protocol.py`：协议处理；
- `control/route_math.py`：路线几何与速度计算；
- `control/route_policy.py`：现有 Wens1 固定路线约束；
- `route_controller.py`：路线装配；
- `logging_utils.py`：每次运行的系统、AGV、JAKA和事件日志；
- `map_utils.py`：地图和 RViz 数据；
- `project_check.py`：不连接硬件的配置预检。

这些底层能力应尽量复用。不要重写 AGV/JAKA 协议，也不要绕过已有安全检查直接发送运动命令。

### 3.3 当前总控制器

`app/wenshi_patrol/patrol_controller.py` 是当前唯一同时持有 AGV 和 JAKA 对象的正式控制点。

它目前负责：

- 路线运行；
- 相机缓存与新鲜度；
- AGV/JAKA 安全互锁；
- 图像采集；
- 当前目标任务状态机；
- 日志和控制台。

这个文件已经很大，不要继续把 Tag、24 株调度、株高算法、有效穗算法和后台处理全部塞进去。

改造原则：

- 仍然只能有一个高层组件拥有 AGV/JAKA 运动控制权；
- 把路线调度、Tag 协调、采集流程、存储和表型计算拆为明确模块；
- 总控制器只编排状态和硬件动作；
- 表型模块只能消费数据并返回结果，不能直接控制 AGV/JAKA；
- 可以逐步重构，不要一次删除现有可工作的路线和安全逻辑。

### 3.4 现有视觉和存储层

`app/wenshi_patrol/vision/` 已有：

- `frame_policy.py`：过期帧拒绝；
- `quality.py`：清晰度、曝光、目标裁切和深度稳定性等质量启发式；
- `targeting.py`：检测选择、RGB-D 深度统计和跨帧目标匹配；
- `detector.py`：YOLO 封装；
- `geometry.py`：像素到相机坐标等几何工具；
- `hand_eye.py`：手眼矩阵读取接口；
- `run_store.py`：当前正式运行/目标存储；
- `storage.py`：当前视觉文件存储边界。

其中帧新鲜度、质量检查、RGB-D 几何、原子 JSON 写入和运行目录隔离可以复用。当前 `run_store.py` 的数据模型是 `targets/T0001/far.jpg/near.jpg`，面向旧目标近拍，不适合直接表示 24 株、三个视角、两个表型和人工复核。需要兼容迁移或新建表型运行 schema，不要把新数据硬塞进 `far/near` 字段。

### 3.5 现有后台

`dashboard/` 当前是运行目录的只读查看和有限管理员操作后台：

- `run_index.py` 读取 `runtime/runs/run_*/targets/T*/metadata.json`；
- `server.py` 提供运行、目标和媒体接口；
- `static/` 显示远景、近景、路线段、侧别和目标质量；
- 管理员功能目前是软删除和去重重置。

后台需要升级为“单株表型后台”，而不是在旧远景/近景页面上简单加两个数字。

### 3.6 现有花时/目标任务代码是什么

仓库里确实有与早期花时想法相关的代码，但它尚未实现花时判定。它目前更准确地说是“发现 rice 后抵近拍照”的目标任务原型：

- `patrol_target_runtime.py`：稳定检测、选取 rice 和运行内去重；
- `target_task.py`：受控后退状态；
- `target_follow.py`：J5 目标跟随；
- `near_capture.py`：近景连拍与质量选择；
- `fixed_approach.py`：固定示教抵近和回撤；
- `patrol_controller.py` 中的 `TARGET_*` 状态：后退、重定位、固定抵近、近拍和恢复路线。

这些代码不是已经完成的花时模块，因为它没有实现：

- “准备开/第一次开花”的判定；
- 颖壳张角；
- 柱头外露或颜色；
- 7:30-8:00 的单株花时记录逻辑。

短期处理原则：

- 保留旧代码和默认关闭状态；
- 不删除，不冒充已完成花时；
- 株高/有效穗流程不要导入旧的后退、目标跟随和固定抵近状态机；
- 可以复用相机新鲜度、质量重拍、存储和安全回撤思想；
- 文档中把旧流程明确标为“保留的研究原型，本期不启用”。

## 4. 建议的新总体架构

不要为株高和有效穗分别创建两个能控制硬件的完整程序。推荐：一个总任务控制器，多个无运动权限的独立模块。

```text
表型巡检总控制器（唯一运动拥有者）
  |- 路线与安全协调
  |- 12 个停车位置调度
  |- Tag 身份与局部触发
  |- 机械臂快速多视角采集
  |- 单株数据存储
  `- 处理任务调度

无运动权限的数据模块
  |- 株高模块
  |- 有效穗模块
  |- 人工复核与结果合并
  `- 花时模块（未来；本期不实现）
```

约束：

- AGV/JAKA 对象不得进入株高、有效穗或后台模块；
- 计算模块失败不得触发底盘或机械臂动作；
- 计算模块可以返回 `ok`、`needs_review`、`failed` 等结果；
- 只有总控制器能决定原地重拍、标记补采、继续下一株或停止任务；
- 普通巡检阶段不允许算法自行倒车。

## 5. 建议的总控制流程

一圈运行主线：

```text
启动检查
  -> 进入中间环路
  -> 根据地图进度寻找下一停车位置
  -> 识别预期 Tag 并确认身份/距离
  -> 减速、底盘停稳
  -> 拍通道左侧植株（三视角）
  -> 机械臂转向，拍通道右侧植株（三视角）
  -> 检查图像完整性、清晰度、深度和 Tag
       |- 合格：保存两株数据
       `- 不合格：当前姿态原地重拍；超限后标记补采
  -> 机械臂回安全巡视姿态
  -> 前往下一停车位置
  -> 12 个位置完成后结束巡检
```

拍摄结束后的处理：

```text
同一株的三视角数据
  |- 株高模块 -> 候选中心线/弧长 -> 人工确认
  `- 有效穗模块 -> 候选穗/跨视角去重 -> 人工确认

最终保存：自动值 + 人工确认值 + 差值 + 修改记录
```

第一阶段允许巡检结束后统一离线计算。接口和数据结构应从一开始支持后台任务处理，后续可改为：一株保存后进入处理队列，机器人继续拍下一株，后台同时计算已拍植株。不要让实时计算阻塞控制循环。

## 7. 统一多视角采集方案

初期建议每株三视角：

1. 左斜视；
2. 正面视角；
3. 右斜视。

原则：

- 正面视角是核心视角；
- 左右斜视补充遮挡，并用于有效穗跨视角去重；
- 机械臂动作要短、快、可重复；
- 优先通过少量关节变化完成，不走旧花时的复杂后退/固定抵近流程；
- 每个姿态到位后等待稳定，只从新鲜帧中选取正式图像；
- 每个姿态可以采短 burst，再选择清晰、曝光正常、深度有效的一帧；
- 机械臂运动过程中的模糊帧不能用于正式测量；
- 每株三视角数据同时交给两个表型模块，不重复采集。

三视角是首期可靠性配置，不是永久结论。24 株人工对照后，应比较：

- 单视角结果；
- 正面 + 一个斜视；
- 三视角结果；
- 每种方案耗时和误差。

再决定是否减少视角。

机械臂三视角姿态尚未现场示教。不要使用当前 `camera_left/camera/camera_right` 名称就假设它们适用于每株表型。现有姿态是旧巡检/抵近项目的姿态，需要现场低速验证，必要时建立独立的表型采集姿态配置。

## 8. 株高模块设计要求

### 8.1 输入

### 8.2 建议处理步骤

```text
1. 确认目标植株和可用视角
2. 找到卡槽顶部参考或已标定起始基准
3. 检测最高穗顶

5. 各视角提取二维中心线候选
6. 利用深度、相机姿态和 Tag 参考恢复/融合三维中心线
7. 对小范围深度空洞做有约束的处理
8. 沿三维中心线计算弧长
9. 加卡槽顶部到水面的补偿
10. 输出候选值、路径、质量和待复核原因
11. 人工确认/编辑路径后保存正式值
```

不要将“图像最高点”作为株高。不要使用深度网络直接回归一个不可解释的数字作为第一版正式结果。

### 8.4 必须标记待复核的情况

- 茎秆/穗轴大段被遮挡；
- 中心线走入邻近茎秆；
- 多视角路径无法一致；
