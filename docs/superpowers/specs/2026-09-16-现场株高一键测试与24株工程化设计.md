# 现场株高一键测试与 24 株工程化设计

日期：2026-09-16

状态：设计稿，待用户审阅

## 1. 目标与边界

Wenshi 当前正式检测范围调整为 24 株：

| 区域 | 植株 | 状态 |
| --- | --- | --- |
| A | A-01..A-08 | 检测 |
| B-L | B-L-01..B-L-08 | 检测 |
| B-R | B-R-01..B-R-08 | 检测 |
| C | C-01..C-08 | 保留 Tag 映射，不检测 |

共 16 个观测停车组。左侧 `left-01..08` 各覆盖 A 与 B-L 两株；右侧
`right-01..08` 各覆盖 B-R 一株。C 排继续贴 Tag 并登记，但状态固定为
`excluded_from_detection`，不得触发 YOLO、株高或有效穗计算。

本设计的交付目标是一个便于现场操作的可行性测试工具，而不是立即放行正式
24 株无人值守巡检。工具必须能在一次运行中保存 RGB-D、调用现有两个模型、
执行多种株高算法并生成可读报告；任何算法失败都必须保留原始证据并标为
`needs_review`，不能伪造数值。

## 2. 用户入口

唯一现场入口：


```bash
./scripts/start_height_test.sh
```

支持的子命令：

```bash
./scripts/start_height_test.sh setup
./scripts/start_height_test.sh arm-only --group left-01
./scripts/start_height_test.sh full-route
./scripts/start_height_test.sh replay runtime/height_tests/run_<id>
./scripts/start_height_test.sh report runtime/height_tests/run_<id>
```

不带子命令进入中文菜单。`arm-only` 只控制 JAKA，AGV 必须已停稳；
`full-route` 控制 AGV 到已设置的 16 个停车点，并在每站调用 JAKA 三视角采集。
两种模式都支持 `stop`/`q`，硬件异常时先实体急停，再使用软件停止。

工具不修改 `phenotyping.enabled`，不复用正式表型控制器的放行锁，也不把测试
结果写入正式 `runtime/runs/run_*`。所有证据写入 `runtime/height_tests/`。

## 3. 现场 setup

`setup` 是引导式、可恢复的现场配置流程，结果写入一次新的
`runtime/height_tests/setup_<timestamp>/`，完成后由操作者明确发布到
`config/field_height_setup.json`；未发布的临时值不能影响正式运行。

### 3.1 Tag 映射

身份 Tag family 固定为 `tag25h7`。每株记录：

- `plant_id`
- `tag_id`
- `tag_size_m`，由现场实测的外围黑色正方形外边长填写，本次标定板为 `0.090`
- `mounting_orientation`（`upward` 或 `side`）
- Tag 可见性和照片证据
- `excluded_from_detection` 状态（C 排为 true）

测量基准板与身份 Tag 分开。测量基准板也使用真实已测尺寸，推荐使用 OpenCV
可直接识别的标准字典；照片中的 `tag25h7` ID 0 可作为身份/兼容检测证据，
不假设当前 OpenCV 原生支持 `tag25h7`。

### 3.2 停车点示教

每个观测组由操作者驾驶 AGV 或使用现场手动控制到目标位置，确认停稳后，
程序读取并保存 AGV 当前位姿：

- `group_id`
- `route_segment`
- `x/y/angle`
- 停车误差和备注
- 两株或一株的 `plant_id` 列表

setup 不自动把地图上的 LM 站点猜成 16 个表型停车点。发布前必须满足 16 个
组各有一个真实位姿；若某站只覆盖 B-R，则不得加入 C。

### 3.3 机械臂视角

优先读取现场已验证的 `viewpoints.json`。若缺少 `home_safe` 或三视角点位，
setup 提示通过已有只读示教流程补齐，不能静默使用旧点位。每个视角在采集前
记录实际 JAKA 关节和 TCP 快照。

### 3.4 水面基准

每个检测株记录 `slot_top_to_water_m`。该值来自直尺实测；缺失时所有绝对高度
候选均为 `needs_review`。Tag 平面用于局部尺度和身份，水面补偿用于把卡槽基准
换算到农艺水面基准。

## 4. 一次测试的数据流

```text
setup/config
    -> 站点和 Tag 预检
    -> AGV 停稳（full-route）
    -> Tag 身份确认
    -> JAKA 到 left/center/right
    -> D435 获取同一 seq 的 RGB + aligned depth
    -> rice_plant / panicle 推理
    -> 五种株高算法并行计算
    -> 多视角融合和质量门限
    -> 原始证据、叠加图、JSON、CSV、HTML/文本报告
```

运动控制、相机采集和算法处理使用独立对象；算法异常不得直接发起运动。
任一视角采集失败时保存失败原因，按策略重试，超过次数后回到安全位并进入
下一株/下一站或等待人工决定。

## 5. 株高方法

所有方法同时运行，结果保存在 `results/<plant_id>.json`。最终主结果先采用
水面到最高穗顶的重力方向垂直高度；沿茎秆的三维弧长作为诊断值。主结果只有
在质量条件满足且与人工尺量配对后才可标记 `candidate`。

### M0：YOLO 框高诊断

保存整株框和最高穗框的像素高度、置信度和图像尺寸，仅用于展示模型尺度依赖。
不转换为正式株高，不参与融合。

### M1：Tag 局部坐标 + 穗顶深度

使用 Tag 已知边长和四角建立当前视角的局部坐标，使用 `panicle` 最高候选框的
上方稳定深度点作为穗顶，计算相对 Tag 基准的垂直分量，再加
`slot_top_to_water_m`。这是第一主自动方法，依赖少、可解释、适合明天验证。

### M2：ROI 点云鲁棒分位数

在 `rice_plant` ROI 内读取 aligned depth，剔除无效值、边缘飞点和明显背景，
对转换后的 3D 点按垂直坐标取高分位数与低分位数差。深度有效率和点数不足时
拒绝。该方法不要求茎秆可见，作为遮挡场景备用。

### M3：植物区域分割 + 垂直包络

在 YOLO ROI 内用 HSV/颜色和形态学得到轻量植物 mask，去除背景后计算垂直包络。
它吸收 PlantCV 的分割思想，但不强制安装 PlantCV 或 scikit-image，便于现有
Ubuntu 环境现场运行。mask 断裂或邻株混入时只保留诊断结果。

### M4：人工辅助最高点

操作者在叠加图中点击基部和最高穗顶，程序从点击邻域读取多帧深度，并使用 Tag
局部坐标计算垂直高度。这是明天的人工基准方法，可区分“模型错误”和“深度/标定
错误”。点击结果不覆盖自动结果。

### M5：人工辅助茎秆路径

操作者沿同一根茎秆、穗轴点击 3 个以上点，程序读取深度并计算三维折线弧长，
再加卡槽到水面补偿。该结果用于比较弯曲植株的路径长度，不替代农艺垂直株高。

### 多视角融合

同一株各视角先在各自 Tag 坐标计算，再按质量加权；默认采用中位数作为融合值，
视角差异超过门限时保留全部结果并标记 `view_disagreement`。没有可用 Tag 或
深度不足的视角不能参与融合。

## 6. 质量门限与成功判据

门限分为设备、检测、测量三层，不把 YOLO 置信度当成株高精度。

### 6.1 设备层

- RGB-D 连续帧成功率 100%（现场测试批次内）；
- `seq` 单调递增，RGB/depth 尺寸一致；
- `depth_scale`、内参和实际 profile 写入每次运行；
- 目标 ROI 深度有效率至少 70%；
- 已知 0.5/1.0/1.5 m 目标的深度中值误差不超过 20 mm 或 2%。

### 6.2 模型层（现场初测）

- 8 株代表性样本中 `rice_plant` 正确识别至少 7 株；
- `panicle` 正确找到最高穗候选至少 6 株；
- 同株连续帧不出现明显跳框；
- 邻株合并、背景误检和最高穗出画必须逐株记录。

### 6.3 株高层（可行性，不是最终产品放行）

- 至少 8 株有人工垂直尺量和自动结果配对；
- M1/M2/M3/M4 的误差、失败率和运行时间全部输出；
- M4 人工辅助结果作为当天基准，若 M1/M2 与 M4 偏差明显，不能宣称自动方法可行；
- 暂定观察线：自动垂直高度相对人工误差中位数不超过 20 mm 或 2%，重复采集
  极差不超过 15 mm。该观察线需根据现场农艺要求重新确认后才能写入正式配置。

测试结束后报告必须明确给出：`camera_pass`、`plant_model_pass`、
`panicle_model_pass`、`height_feasibility_pass`，允许部分通过；不能用一个总的
“成功”掩盖某层失败。

## 7. 证据目录

```text
runtime/height_tests/run_<timestamp>/
  run.json
  setup_snapshot.json
  events.jsonl
  summary.json
  report.html
  report.csv
  stations/<group_id>.json
  plants/<plant_id>/
    views/<left|center|right>/
      color.jpg
      depth.png
      frame.json
      detections.json
      overlay.jpg
    results.json
    manual.json
```

原始 RGB、depth 和元数据只写入新目录，不覆盖训练数据、正式运行目录或历史现场
证据。`replay` 只读取该目录重新计算，不连接硬件。

## 8. 配置和依赖策略

新增独立的 `height_test` 配置段，默认关闭自动运动，显式通过命令参数选择
`arm-only` 或 `full-route`。模型路径分别指向当前 `rice_plant` 和 `panicle`
产物，不能复用旧 `vision.model_path` 的单模型语义。

第一阶段只要求当前已有的 Python、OpenCV、NumPy、PyYAML 和 ultralytics。
AprilTag 后端采用可插拔适配器：`tag25h7` 使用已验证的可选后端；OpenCV 原生
缺少 `DICT_APRILTAG_25h7` 时必须在预检中明确报错，不得静默按 ArUco 解码。
Open3D、PlantCV、SciPy 和 scikit-image 作为后续增强依赖，不成为明天一键测试的
硬依赖。

## 9. 正式代码整理原则

保留 `yubei/` 数据采集、标注和训练工具，不在本次删除其历史兼容入口。

正式项目按以下边界整理：

1. 新增 `height_test` 子系统，不把逻辑塞进 1593 行的旧
   `patrol_controller.py`。
2. 运动只复用经过测试的 `agv.py`、`jaka.py`、`arm_controller.py` 和路线数学，
   不让视觉算法直接导入运动客户端。
3. `vision/detector.py` 保留为通用 YOLO 包装；新增整株/稻穗模型适配和结果
   序列化，不修改旧 rice 目标跟随协议。
4. 旧 `rice/flower`、J5 跟随、倒车和固定抵近模块先标记为兼容/实验边界，完成
   引用图和回归测试后再移动到 `legacy/` 或归档；本次不做无证据硬删除。
5. 清理只针对正式目录中的无引用代码、缓存和重复入口；`yubei` 原始数据和
   训练产物不删除。

## 10. 分阶段交付

### Phase 1：现场可行性工具

- `setup`、`arm-only`、`full-route`、`replay`、`report`；
- RGB-D、Tag、模型检测和 M0-M5 结果；
- 设备/模型/测量分层判据；
- 单元测试和无硬件 replay fixture。

### Phase 2：现场数据后收敛

- 根据报告确定主算法和阈值；
- 补齐当前设备手眼闭环和重力方向；
- 将确认的 24 株配置写入正式配置；
- 解决 C 排排除和 16 个停车组的正式预检。

### Phase 3：正式表型接入

- 只有 Phase 1/2 证据满足要求后，才考虑接入正式
  `phenotyping_controller` 和后台正式结果。
